# Mac 悬浮窗 Enter 发送与接收确认

## 定位与调整

- 原先字幕窗调用 IPC 成功，只代表事件已转交主窗口，不代表已通过配置、设备检查或进入发送队列。主窗口忙碌时可能直接返回，字幕窗却提前清空文字。
- 发送增加独立请求标识，主窗口在队列实际接收时返回确认；忙碌、页面不符或预检查失败时明确拒绝。IPC 转交成功不再清空输入。
- 只清空已确认接收、且用户没有继续编辑的那版草稿。拒绝保留原文；上一条输出完成不再清空下一条录音或输入草稿。
- 接收确认除事件推送外，在等待期间读取同步快照，恢复窗口切换时漏收的确认。发送期间防止重复提交，按钮显示等待动画，输入框仍可编辑。
- 输入法组合状态同时使用 composition 事件、`isComposing` 和 229 兼容值，失焦时清理组合状态。选词 Enter 不发送，选词后再次 Enter 发送；Shift + Enter 换行，长按 Enter 不重复发送。提交读取当前输入框内容，避免组合结束时 React 状态尚未更新。

这些共享输入和确认逻辑同时适用于 Windows，不修改 Mac 原生面板层级和输入法激活策略。

## 验证范围

- 前端 301 项测试通过，覆盖接收和拒绝后的草稿保留、下一条编辑保护及现有组合键逻辑。
- Mac Rust 176 项测试通过，23 项设备/外部服务测试忽略；包括请求标识序列化、确认状态和错误长度边界。
- 隔离浏览器加载真实 `OverlayVoiceControls`，模拟 Tauri 消息传输：组合输入 Enter、重复按键、等待期间编辑、主窗口拒绝、Shift + Enter、确认事件漏收后读取快照均通过。未调用服务、读取真实配置或播放音频。
- 前端格式、Rust 格式及 Mac 生产打包、签名和麦克风 entitlement 检查通过。本机应用覆盖更新，不主动重启。

浏览器中的 composition 事件模拟不能替代所有 macOS 输入法与全屏应用组合的实机测试；本次修复针对已定位的发送确认缺失和输入处理问题，不宣称已复现所有用户遇到的间歇场景。
