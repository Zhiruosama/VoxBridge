# macOS 悬浮窗输入法候选框

[验证记录](README.md) · [排错指南](../guides/troubleshooting.md)

## 问题

在其他应用的全屏桌面上，字幕悬浮窗可以接收拼音和提交汉字，但不显示候选词框；同一 Chrome 页面自己的输入框正常。另一次原生编辑器实验还造成了占位文字与输入内容重叠。

只检查 DOM 焦点、key window 或截图不够：系统可以把键盘事件交给非激活面板，而候选 UI 没有进入当前全屏桌面。单窗口截图也能截到其他桌面上的窗口，不能据此判断实际可见性。

## 当前处理

- 被动字幕继续使用非激活 `NSPanel`，保留原有跨桌面、跨全屏显示与拖动缩放逻辑。
- 显式打开文字输入时，创建一个**从分配时就采用可激活样式**的编辑面板。它使用 `MoveToActiveSpace | FullScreenAuxiliary`，层级为普通 floating（3），低于系统候选窗口（20）。
- 迁移同一个网页根视图，保留草稿、事件与 Tauri IPC 身份；不重新加载页面，不改 Tao 宿主窗口的类、代理或布局。迁移两端均保留合法的 content view。
- 编辑期间暂时采用辅助应用模式。Dock 图标在此期间可能消失；收起、隐藏输入窗时恢复原来的应用策略与字幕面板。
- 已打开的编辑框被再次点击时，原生层重新请求 key 和应用激活，不依赖 DOM focus 再次触发。异步焦点任务受窗口编号与编辑轮次限制，失效任务不会重新抢焦点。
- 切到新的桌面且编辑面板已不在当前 Space 时，恢复原来的跨桌面字幕显示；下一次显式点击再建立当前桌面的编辑面板。
- 文字输入恢复为网页 textarea；撤掉未解决问题的原生 NSTextView 实验，避免两套输入内容及占位提示重叠。输入法组合期间不执行发送或收起快捷键。

不在已有面板上直接切换 `NonactivatingPanel` 位，也不修改 Tao 的 Objective-C 类。Windows 保持原来的输入实现。

## 本轮实机证据

使用独立的本地全屏测试应用和实际字幕面板实现，不读取配置、密钥或剪贴板，不调用 ASR、翻译、TTS，也不发送聊天消息。

| 检查 | 结果 |
| --- | --- |
| 原有非激活面板在全屏桌面输入拼音 | 接收组合文字，候选窗未出现在实际屏幕窗口列表中 |
| 新编辑面板输入系统简体拼音 `ni` | 系统实际屏幕列表中存在候选窗，层级 20，位于输入框光标旁 |
| 位置对照 | 编辑面板约 `(514,196,700,380)`；候选窗约 `(539,364,397,28)`，均由测试进程呈现 |
| 空格选词 | 输入内容变为“你” |
| 收起编辑 | 草稿仍为“你”，恢复被动面板 |
| 五轮生命周期回归 | 同一网页根视图在两面板间迁移；重复打开幂等；隐藏不残留编辑窗；应用策略恢复 |
| 隐藏面板输入请求 | 拒绝激活；结束输入不会意外显示隐藏面板 |

测试工具的按钮原先调用了未授权的独立测试命令，导致切换输入法与关闭按钮无效。现统一通过**测试二进制自己的**现有授权命令处理显式测试操作；没有扩展生产应用的权限。输入源切换按钮只用于测试，结束时选择 ABC 恢复。

281 项前端测试、170 项 Rust 测试通过；23 项显式忽略的集成测试未运行。原生生命周期回归、格式、文档链接、Mac 打包与签名检查通过。

独立全屏桌面的候选词已验证。用户原来使用的 Discord／Chrome 全屏工作区、多显示器组合仍需安装后持续观察，不能以编译或单窗口截图代替其全部实机验收。

## 复测方法

1. 启动本地开发服务：`npm run dev`。
2. 在允许显示测试窗时运行 `cargo run --manifest-path src-tauri/Cargo.toml --example overlay-ime-regression`。
3. 在另一个应用的全屏桌面打开测试输入框，明确选择“系统拼音”，用真实按键输入并选词。
4. 收起后再次展开，检查草稿、占位文字与选词；退出全屏后再检查一次。测试完选择 ABC 并点“完成测试”。工具最长运行十分钟。
5. 运行 `cargo run --manifest-path src-tauri/Cargo.toml --example overlay-ime-regression -- --self-check`，验证窗口迁移与恢复。此检查会短暂显示独立测试窗，不在用户工作时自动运行。

## 已排除的尝试

仅降低窗口层级、重申 first responder、刷新候选坐标、延迟等待应用激活、临时让面板成为 main window、只改 Space 标志、同一非激活面板内换成原生 NSTextView，均未通过用户原场景验证。没有保留这些无效的替代方案。

参考：[Apple NSPanel 焦点策略](https://developer.apple.com/documentation/appkit/nspanel/becomeskeyonlyifneeded)、[Apple moveToActiveSpace](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/movetoactivespace)、[Apple 关于辅助应用全屏悬浮窗的讨论](https://developer.apple.com/forums/thread/826308)。
