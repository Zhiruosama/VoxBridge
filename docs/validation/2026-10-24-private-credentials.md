# 私有本机凭据存储与真实重启验收

[验证索引](README.md) · [当前使用指南](../user-guide.md)

> 历史验证记录：仅说明记录日期的测试范围，不代表所有平台、客户端或后续构建均通过。

## 原因与参考

用户实测仍需要重新配置。检查时，磁盘只有旧 `credentials.v1.enc`，没有上一版新增的日常凭据文件；旧模板与日常保存两条路径没有消除使用上的分叉。当前 `.app` 使用临时签名，其指定要求是 `cdhash`，每次构建变化。此前只测试相同测试程序重启，没有覆盖实际应用更新和重新签名。

查阅的上游实现：

- [Chatbox 的桌面持久化实现](https://github.com/chatboxai/chatbox/blob/main/src/main/store-node.ts)：使用应用 `userData` 下的 `config.json`、electron-store 和本地备份，普通设置持续保存，不要求用户每次启动导入模板。
- [Chatbox 的存储分层](https://github.com/chatboxai/chatbox/blob/main/src/renderer/platform/desktop_platform.ts)：桌面 IPC 文件存储与 IndexedDB 分工。
- [Electron safeStorage 官方说明](https://www.electronjs.org/docs/latest/api/safe-storage/)：macOS 密钥保护依赖钥匙串及一致的应用签名，签名不一致的构建可能导致更新后重新请求授权。不能靠禁止授权 UI 来解决签名连续性。

采用本机私有文件方案，移除模板和日常保存两套流程，不放宽钥匙串 ACL、不更改系统密码或签名信任设置。

## 存储与边界

- 主窗口只保留保存和移除密钥；模板的前端、IPC 命令和权限入口均删除。
- 使用应用数据目录下的 `credentials/`，Unix 目录权限 `0700`，文件权限 `0600`。
- `keys.v1.enc` 使用 AES-256-GCM、随机 nonce、认证文件头及原子替换；随机的 32 字节主密钥保存在独立的 `master.v1.key`。内存中的主密钥、凭据映射和加解密缓冲区使用 zeroize。
- 这是当前系统用户文件权限保护，**不是钥匙串提供的同一用户下应用隔离**。可读取这两个文件的同一用户程序可以解密数据。不能把它描述成与系统钥匙串同等安全；备份应保护整个私有目录。
- 密钥不进入普通配置、前端 localStorage、日志或 Git。日常保存、读取、删除、重启和重新打包均不访问系统凭据存储。
- 新存储尚不存在时，只对旧加密格式尝试无弹窗迁移；优先日常密钥，再补充旧模板中的其他条目。保留旧文件，不自动选择或切换配置。
- 已有新存储时不再读取旧凭据，删除全部密钥也保存空映射，防止重启后重新导入旧密钥。
- 损坏、主密钥缺失、写入失败时保留原文件，不自动重新生成主密钥覆盖旧数据；失败不会更新内存或提示保存成功。拒绝符号链接密钥文件。

## 验证结果

- 105 项前端测试、121 项 Rust 常规测试通过；21 项手工测试默认忽略。格式检查、Clippy、前端构建、Mac `.app` 打包及签名校验通过。
- 覆盖持久保存、更新、删除、重启、空配置无文件操作、私有权限、加密文件无明文、迁移优先级、迁移失败后正常保存、删除后不重新导入、损坏与主密钥缺失、原子写入失败和符号链接拒绝。
- 跨进程测试复制并重新签名测试程序，新的进程无需授权即可读取原凭据。
- 构建隔离的真实 `.app`（`com.voxbridge.persistence-validation`），通过原生界面保存无效的合成测试字符串，完整退出并重开，状态仍为“已保存”。再更换应用代码签名并重开，状态仍为“已保存”。没有调用服务、没有向正式用户配置写入测试字符串。
- 对正式应用已保存的三组密钥进行了无弹窗迁移，只记录恢复数量，不输出密钥。新文件实际权限为目录 `0700`、两个文件各 `0600`。
- 正式应用完整退出、启动新版后，文字翻译、语音识别、语音合成三个设置页均直接显示“已保存”，未输入密钥或载入模板。
- 重启后使用自动恢复的翻译密钥完成一次实际翻译；未输出语音到设备或通话。
