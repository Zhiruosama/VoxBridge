# Windows 首次使用虚拟麦克风的配置阻塞

[验证索引](README.md) · [语音发送指南](../guides/voice-output.md)

## 报告与原因

外部 Windows 0.5.1 排查报告显示：官方基础 VB-CABLE 的输入/输出设备存在且活动；实际持久化发送路由却指向 Realtek 扬声器。另一个独立阻塞是输出选择了译文，而活动翻译配置没有地址与模型。日志未记录语音合成或播放启动，因此不能归因为已经证实的驱动传输失败，也不能宣称 QQ 端到端正常。

## 修复

- 新配置使用 `__virtual_microphone__` 自动发送目标。后端只解析完整、无歧义的基础虚拟设备对，发送前绑定为具体稳定 ID；未就绪、半安装或重复设备会失败，不改用系统扬声器。试听默认仍跟随系统输出。
- 有效持久化配置、明确的系统默认、扬声器选择和不可用端点 ID 均保留。用户主动点击工作台快捷按钮才改变发送路由；不修改系统默认播放或录音设备，不自动重装驱动。
- 工作台只读检查并展示实际发送设备、对应聊天输入、配置入口及原文快捷操作。枚举未完成时显示检测中，不先冒充设备已断开。录音后填入文字和结束后发送均有明确说明，不承诺原声直通。
- 设置页区分当前选择和已保存路由；点击「用作发送设备」但尚未保存时显示「保存更改后生效」。
- 提交前检查 TTS 配置、实际需要的翻译配置与输出/监听设备。失败不清空草稿、不接受进队列、不调用翻译或合成。输入已经是目标语言时仍可跳过翻译配置，并复用识别结果，避免重复检测。后端发送前继续保留设备校验。
- 原有测试音按钮不依赖云服务，但只能证明播放任务结果，不能冒充虚拟输入回环或 QQ 收音验证。

## 自动验证

- 回归报告中的空翻译配置阻断、原文发送绕过翻译配置、同语言绕过及检测复用、TTS 配置缺失、发送设备不可用、监听设备检查和仅文字翻译无需音频。
- 回归旧用户明确设备选择不变、空配置采用自动虚拟目标、迁移不把新标识当设备名称、双端缺失/单端/partial 均拒绝，完整设备对返回指定 ID。
- 编辑已排队文字会废弃原文的预检语言结果并重新判断；原文与译文不会因为沿用旧语言而走错流程。
- 278 项前端测试、171 项默认 Windows Rust 测试通过；25 项手动测试默认忽略。严格 Clippy、格式与前端生产构建通过。
- 单独运行只读硬件检查：自动虚拟发送与等待设备函数均解析到当前已验证 VB-CABLE 设备对的稳定输出 ID，没有打开输入或输出流。
- Windows x64 开发安装包生成成功。本机覆盖更新后工作台显示实际 VB-CABLE 输出及聊天输入；持久设置逐字节相同，凭据文件指纹相同。

## 边界

报告来自另一台电脑，本次不访问其系统或秘密配置。不在正在进行的通话中发送测试音，不调用收费服务或录制实体麦克风。需要对方安装本次修复包后，按指南核对路由并发送一条实际语音，才能确认其 QQ 通话已经恢复。
