## 修复

原先文字表达在监听时反转监听方向，覆盖设置中的输出语言；自动识别监听模式下又回落到默认的中文 → 英语，容易让语言选择看起来没有效果。

现在输入框旁直接显示“语音目标语言”，与设置页中的输出语言同步。文字表达固定使用用户选择的目标，不随监听状态变化；上方“字幕语言”只控制监听字幕。

- 保留简体中文、英语、日语、韩语、西班牙语五种目标。
- macOS 使用系统 NaturalLanguage 框架离线识别实际输入，概率低于 0.8、混合文字脚本或不支持的语言返回不确定；其他平台使用保守的 Whatlang 可靠性判定。不会因为输入语言下拉框与目标相同，就假设文字实际属于该语言。
- 实际输入与目标一致时跳过翻译配置校验及翻译请求，原文直接进入语音合成。字幕区相同原文和译文只显示一次。
- 不确定的内容继续正常翻译。识别期间锁定当前操作，可停止，不会启动取消后的翻译或语音；后续草稿仍可编辑。
- MiniMax WebSocket `task_start` 传递对应的 `language_boost`；OpenAI-compatible 语音接口使用目标语言文本。不支持的语音语言会显式报错，不静默回落英语。
- 翻译结果被本地识别为另一种支持语言时，复用现有校验重试，重复失败只返回错误，不把错误语言当作成功译文。

MiniMax 参数依据[官方 WebSocket 文档](https://platform.minimax.cn/docs/api-reference/speech-t2a-websocket)。其他平台离线识别依据 [Whatlang 官方实现](https://github.com/greyblake/whatlang-rs)；短句或混合语言不能保证识别，因此保留正常翻译回退。

## 验证

- 前端 105 项测试、Rust 120 项常规测试通过；20 项手工测试默认忽略。
- 常规测试中曾出现一项实时 ASR 模拟连接时序失败，未修改相关代码的完整重跑通过。
- 覆盖五种目标从选择到翻译/TTS 的传递、监听不覆盖输出方向、同语言跳过翻译及翻译配置要求、错误输入语言提示不导致误跳过、识别期间重复提交和取消、短聊天句离线识别，以及实际 WebSocket 消息的语言参数。
- 独立浏览器测试真实 React 界面：选择日语后中文输入调用一次翻译，随后日文输入直接合成，翻译计数保持一次。截图在忽略目录 `native/macos/.build/target-language-ui.png`。
- 单独执行付费测试 `live_tests::live_selected_languages --exact --ignored --nocapture`，凭据从用户指定的测试文件通过 stdin 传入，不写入应用配置或系统凭据。四次 DeepSeek 翻译、五次 MiniMax 合成全部通过；中文同语言场景未请求翻译。

| 目标 | 翻译与合成总耗时 | 返回音频 |
| --- | ---: | ---: |
| 英语 | 2275 ms | 113517 bytes |
| 简体中文（直读） | 1092 ms | 140589 bytes |
| 日语 | 2484 ms | 160173 bytes |
| 韩语 | 1867 ms | 173421 bytes |
| 西班牙语 | 1903 ms | 139437 bytes |

每条译文均通过实际语言识别，音频可解码且非静音。耗时是这次测试完整返回耗时，不代表播放首帧延迟；未打开物理音频设备或向聊天通话输出，也未对音色口音作主观验收。

前端构建、格式检查、Rust Clippy、Mac `.app` 构建和签名校验通过。没有重启用户正在运行的应用，新版在重启后生效。
