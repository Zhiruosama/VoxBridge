# macOS 音频、权限与设备路由

## 1. 系统基线与验证范围

建议最低 macOS 14.2、首测 Apple Silicon。Apple 官方 Core Audio taps 示例要求 macOS 14.2+，支持采集进程或进程组的输出，并要求配置 `NSAudioCaptureUsageDescription`。这支持本设计的方向，但不代表当前仓库已具备采集能力。[Apple 官方示例](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)

原型以本地 `.app` 运行、站外分发方向验证。首轮不处理 App Store 沙盒发布。最终权限、签名及桥接配置以 Mac 构建结果和官方要求为准，不预先声称某个 entitlement 可以解决全部权限问题。

## 2. 接收链路

```text
Discord / 浏览器目标进程
  → Core Audio process tap
  → 私有 aggregate device / IO callback（按官方示例验证）
  → 有界 PCM 缓冲
  → 后台声道转换 + 重采样
  → ASR 所需格式
```

- 优先按目标应用捕获，降低通知声、试听声和自身输出混入的概率。
- 浏览器和 Discord 可能通过子进程播放声音。枚举应用不等于已正确识别音频进程，必须验证进程归属、重启和子进程切换。
- 全系统采集只作为显式备用模式；当无法排除自身声音时，禁止与发送 / 试听同时启用并提示原因，不默默形成回环。
- 首选 Core Audio taps。只有实机证明不满足要求时，再评估 ScreenCaptureKit 等替代方案；不在首版并行维护两套采集后端。
- 原始格式来自设备协商，不能假定固定 48 kHz / 双声道。ASR 转换目标取决于服务要求，16 kHz 单声道仅为常见候选值。

生命周期：解析应用 → 创建 tap → 配置关联设备 → 注册并启动回调 → 后台消费；停止时先禁止新数据，再停止回调、注销回调并释放设备 / tap。任何中间失败都反向清理。反复启停不能遗留设备或重复采集。

## 3. 输出与虚拟麦克风

原型建议用户独立安装 BlackHole 2ch。BlackHole 是将音频在应用间路由的 macOS 虚拟音频驱动；这解决“聊天软件能选择输入设备”的问题，不承担翻译功能。[BlackHole 官方项目](https://github.com/ExistentialAudio/BlackHole)

```text
发送：VoxBridge 合成音频 → BlackHole 输出端 → Discord 选择 BlackHole 输入端
试听：VoxBridge 合成音频 → 用户耳机（不经过 BlackHole）
接收：Discord 的远端声音 → 用户耳机，同时由目标进程 tap 采集
```

配置约束：

1. Discord 输出设为真实耳机，输入设为 BlackHole。
2. VoxBridge 的发送设备设为 BlackHole，试听设备设为真实耳机。
3. VoxBridge 的真实麦克风输入（后续增量）必须为物理麦克风，不能默认跟随已被设为 BlackHole 的系统默认输入。
4. 不把 BlackHole 自动设为系统默认输出；不要求用户把全部系统声音导入虚拟线路。
5. 原型不启用真实麦克风与 TTS 自动混音。需要混音时另行设计音量、静音和回声处理。

设备名称不作为唯一标识，保存 Core Audio UID。设备失联立即停止对应输出；禁止偷偷回落到扬声器或其他设备。重新连接后让用户确认目标，再显式恢复。

本阶段不捆绑、修改或自动安装驱动。未来若需随应用分发，另行核对项目许可证、分发授权与安装体验；当前不据此推断闭源分发许可。

## 4. 防回环与通话处理

- 默认目标应用采集应排除 VoxBridge 自身进程；在 Mac 上证明目标进程 tap 确实隔离。
- 不将 TTS 音频回灌到接收 ASR。
- 耳机为首测配置。扬声器可能通过物理麦克风产生声学回声；不承诺自动回声消除。
- Discord 自身的降噪、门限和语音活动检测可能截断合成语音。先在其麦克风测试中验证，再与对端回听；具体设置建议以实测为准。
- 按住说话模式下，必须由用户保证 Discord 发话开关覆盖整个合成播放；VoxBridge 首版不模拟 Discord 快捷键。

## 5. 权限与设备状态

| 情况 | 产品行为 | 验证方式 |
| --- | --- | --- |
| 系统音频权限未授予 | 用户点击监听后请求；失败显示原因与设置引导 | 首次安装、拒绝、再次授权 |
| 麦克风权限未授予 | 仅在启用真实麦克风功能时请求 | 文本 TTS 不应要求麦克风权限 |
| 权限撤回 / 采集失败 | 停止会话，释放资源，可重试 | 运行时改变权限并重新启动验证 |
| 目标进程退出 | 提示重新选择，不持续空转计费 | 退出并重开 Discord / 浏览器 |
| 输出设备断开 | 停止播放并清空，显示设备丢失 | 拔耳机、移除或重启虚拟设备 |
| 睡眠 / 唤醒 / 蓝牙切换 | 停止并重建必要的音频资源 | 不把唤醒前残留音频重新播放 |

真实麦克风使用时需相应的 `NSMicrophoneUsageDescription` 等平台配置；实际授权流程单独在 Mac 验证。Core Audio taps 的权限不能与麦克风权限混为一谈。

## 6. 悬浮窗原生边界

悬浮窗先使用 Tauri 窗口能力，实现透明、无边框、置顶与鼠标穿透；若 macOS 全屏 Space 行为不足，再加入最小原生窗口适配。必须提供主窗口开关与托盘 / 菜单入口恢复交互。验收普通桌面、多显示器、全屏 Space；未通过前不宣称所有全屏应用上方可见。

## 7. 首轮 Mac 探针

先逐项证明：能构建运行 → 正确请求系统音频权限 → 采集指定应用并看到电平 → 耳机播放测试音 → BlackHole 回录测试音 → Discord 对端听见 → 同时收发无数字回环。任一步失败，先记录原生问题，不继续叠加 AI 服务掩盖音频故障。
