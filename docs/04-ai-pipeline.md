# AI 流水线、延迟与成本

## 1. 服务选择状态

| 阶段 | 建议 | 状态 |
| --- | --- | --- |
| ASR | 先接一家提供流式识别的云服务 | 厂商、地区、模型、语言支持待选 |
| 翻译 | 低延迟文本模型，独立 TranslationProvider | 用户提及的“ds flash”具体服务 / 型号待确认 |
| TTS | MiniMax 流式接口为首候选 | 账号区域、模型、音色和格式待验证 |
| 本地 ASR | sherpa-onnx 流式模型作为评测候选 | 非首个原型硬依赖 |

MiniMax 官方提供 WebSocket TTS 接口，但“支持流式”不等于在目标网络和语言下达到延迟目标。[官方 TTS 文档](https://platform.minimax.io/docs/api-reference/speech-t2a-websocket)

sherpa-onnx 提供流式模型目录，可以用于本地识别评测。不同模型支持的语言与硬件不同，不承诺一个小模型覆盖全部语言。[官方模型目录](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/index.html)

本轮不填写未经确认的模型名、价格、接口参数或 API 地址；实现选型时核对供应商官方文档并记录验证日期。开发前置条件是至少拥有一种可用 ASR、翻译和 TTS 凭据；凭据未就绪时可用模拟服务验证流程，不能视为真实模型已通过。

## 2. ASR 与短句策略

1. 以服务要求的帧格式连续发送音频，支持其 partial / final 事件。
2. partial 只更新当前原文，不直接进入 TTS。
3. 优先依据 ASR final 提交短句翻译；final 过慢时再评估稳定前缀策略。
4. 应用自己的静音切句只用于服务不提供可靠端点时的后备策略，避免双重切句。初始静音窗口可试 400–700 毫秒，须按目标语言评测。
5. 长段发言通过标点 / 服务端分段切成可理解短句，不无限等待一句话结束；强制切段须记录为性能与质量取舍。
6. 每句携带 segment_id 和 revision，译文回写必须匹配源修订。重复 final 不重复请求；新会话不复用旧句标识。

字幕原文允许修订，译文默认在 final 后生成。第一版不以每个 token 触发翻译；若追求更低延迟，后续再增加限频的稳定前缀翻译。

## 3. 翻译策略

- 默认明确指定源语言和目标语言；首测中英双向。
- 只输出译文，保留否定、数字、单位、称呼与专有名词；不回答转录内容中的问题，不把用户语音当系统指令。
- 上下文建议保留最近 3 个定稿短句，并设置 token 上限；切换语言 / 会话时清空。
- 字幕翻译和发送翻译是两个独立请求用途；接收译文不自动朗读。
- 翻译失败保留原文并标注，可手动重试；不使用旧译文伪装新结果。
- 服务输出为空、被截断或语言异常时显示失败状态，避免静默发送。

## 4. TTS 与播放

文字表达：输入 → 可选翻译完成 → 用户已选择的试听或发送路由 → TTS 流式合成 → 解码 → 格式转换 → 有界播放队列。

第一版先对完整输入或完整译文启动流式合成，不把未确认的翻译 token 直接朗读。后续若支持分句发送，必须保持句序、只发送确认片段，并允许取消剩余部分。

适配器必须声明真实编码、采样率和声道；不能将 MP3 压缩片段直接当 PCM 播放。解码器处理跨网络分片的音频数据，不假设每个响应片段是独立文件。

停止后：清本地播放队列 → 更新 generation 拒绝旧分片 → 取消合成流。已经进入设备和远端通话的缓冲不可撤回。播放一旦开始，断线后不自动重放整段，避免对方听见重复语音。

## 5. 网络与错误

- 建议连接超时初值 10 秒、翻译请求超时 15 秒；流式服务需单独定义首结果与持续无响应超时，长连接不能套用普通请求总超时。
- 仅对临时连接失败 / 明确可重试的限流执行有限重试，建议最多 2 次，指数退避加抖动；尊重 Retry-After。认证、余额不足和配置错误不自动重试。
- ASR 重连新建流、标记断档，默认不重传旧缓冲音频，避免重复字幕与计费。
- TTS 首音播放后不自动重试；播放前失败也需明确避免重复提交计费，接口无幂等保障时交由用户重试。
- 各链路独立降级：翻译失败可继续原文字幕；TTS 失败不停止接收；采集失败停止对应 ASR 请求。

## 6. 延迟度量

记录单调时间戳：语音开始、首个原文、短句结束、ASR 定稿、翻译请求 / 完成、发送点击、TTS 请求、首个可解码音频、本地首帧输出、停止点击、本地最后一帧。

必须同时报告：

- 语音开始 → 首原文：体现流式反馈。
- 语音短句结束 → 译文完成：包含 ASR 端点等待，不能只报模型推理耗时。
- ASR 定稿 → 译文完成：分离翻译服务耗时。
- 点击发送 → 虚拟输出首帧：按是否翻译分别统计。
- 对端可听时间：需要 Mac 与对端回听单独测量，不能拿本地首帧替代。

记录 p50 / p95 和失败率，标明样本条件；不把语速、语义等待与网络耗时混成一个无法解释的“实时”数字。初始目标见[验收标准](01-requirements.md)。

## 7. 费用与预算

```text
总费用 = ASR 计费音频时长 × 单价
       + 翻译输入 token × 输入单价 + 输出 token × 输出单价
       + TTS 计费字符数 × 单价
       + 可能的自有服务费用（首版无自有服务）
```

具体单位按供应商账单换算。预算示例只记录用量：每天监听 60 分钟、发送 3,000 字、每月使用 20 天，对应约 1,200 分钟识别、60,000 字合成，翻译量另计；不是价格报价。TTS 使用翻译后的计费字符量，不等于输入框字数。

控制策略：暂停立即停止上传；识别定稿去重；上下文限长；限制单次输入长度（初始建议 500 字符，且不超过服务上限）；忙时不积压发送；原型按会话显示估算用量。

客户端用量只能估算，重试、服务端计费单位和账单延迟可能造成差异。后续预算阈值可以阻止新请求，但不宣称客户端限额等于供应商硬性扣费上限。

## 8. 本地 ASR 决策门槛

使用同一组中英语料在 Mac 上测云端与本地：漏字 / 错字、首结果与定稿延迟、CPU、内存、发热、模型体积、离线可用性。若本地质量和资源开销可接受，再决定是否默认启用；目前不把“本地必定更快、更便宜”作为结论。
