## 结论与首版边界

沿用现有 React、Tauri 和 Rust 供应商适配器。主要新增工作是 Windows 应用采集、来源身份和恢复、稳定输出端点、平台体验及安装分发。建议首版验收 Windows 11 x64；本机结果不能代表 Windows 10 或 ARM64。

优先交付两个可独立验证的结果：

1. 选择应用 → 采集其进程树声音 → 实时 ASR → 双语字幕与浮窗。
2. 文字/录音 → 可选翻译 → TTS → 指定输出；通过已有虚拟音频设备接入 Discord，并独立控制试听。

自有 VoxBridge 虚拟麦克风驱动作为独立后续里程碑。WASAPI 监听与播放不会自动创建录音端点。

### W2 / P0：WASAPI 应用进程树采集

- [x] 增加 Windows API 依赖与 build 检测，低版本明确拒绝，不回落成整个系统采集。
- [ ] 枚举可选应用并映射目标进程树，排除 VoxBridge 自身；受保护/已退出进程给出可理解的状态。
- [x] 实现 Application Loopback、COM 生命周期、静音、PCM 转换及有界缓冲；激活中取消与反复释放验证通过。
- [x] Windows 输入接入已有 stereo 帧、重采样和断点统计，静音持续提供帧。
- [x] 接入共用诊断、HTTP/实时 ASR 与翻译；受控进程树隔离、20 次启停和本地服务恢复通过，真实供应商另验。
- [ ] 受控目标播放/静音、另一应用同时播放、连续启停至少 20 次、目标退出/重启、音频子进程重建、断网/恢复和手动停止尾句验收。

**完成标准：** 目标应用字幕闭环可用，其他应用声音不混入；停止后无继续采集，无旧字幕回流，重连不重放旧音频。

依据 [Microsoft Application Loopback 官方示例](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)，这条 API 路径可限定进程及子进程，示例要求 build 20348+。本机 build 高于门槛，只说明具备评估条件，仍需实测。

### W3 / P1：设备身份、输入权限和安全路由

- [ ] 输出 ID 从设备名称改为稳定 Windows 端点标识。本轮已核对下载的 CPAL 0.17.3：WASAPI `Device::id()` 调用 `IMMDevice::GetId`，优先复用现有 API，并验证真实设备标识往返。
- [ ] 对旧名称配置明确迁移/重选规则；重名、缺失、歧义均不得随意选第一个设备。
- [ ] 明确 `__system_default__` 对应的设备角色，保持动态解析；当前 CPAL WASAPI 默认端点采用 `eConsole`，需要将这一现状与产品预期核对。显式设备消失时保留等待/取消语义，不回落到外放。
- [ ] 验证现有麦克风 `mic:` ID 在 Windows 的稳定性，补隐私设置拒绝、独占占用、不支持格式与错误分类；非 Mac `permission()` 返回 Ok 不代表获得授权。
- [ ] 审核虚拟输入过滤逻辑：当前 `physical()` 主要排除 VoxBridge 名称/ID，不能据此声称其他第三方虚拟输入均被排除。
- [ ] 真机验证 USB/蓝牙热插拔、默认设备切换、睡眠唤醒及播放中取消；确认不会自动重发已播放的语音。

**完成标准：** 精确输出到所选设备，重启后标识仍可解析，断连和权限问题可恢复且不会误播。

## 推荐下一批开发

先完成 W0 的换行与 Rust/独立 exe 基线，再做 W1 的最小采集门面及来源身份设计，随后交付 W2 的纯本地采集诊断。取得目标非零电平、非目标隔离和停止释放的证据后，再联调真实模型。

W3、W5 可在采集闭环前穿插推进；W4 依赖安全输出路由；W6 的音频验收依赖 W2–W5。W7 不作为第三方虚拟设备首版的前置条件。不按文档篇幅估算工期，待最小 WASAPI 原型和 Rust 基线通过后再拆具体开发批次。
